# Sitlab

A creative lab for developing characters, stories, plot lines, humor and drama, character arcs,
storyboards and screenplays, drawing on researched public sources. It is an installable PWA backed by
a Strapi CMS.

Sitlab is also the first real application of [strapi-php](https://github.com/hynding/strapi-php).
The same content model runs on two backends side by side:

| App | What | Port |
| --- | --- | --- |
| `apps/cms-php` | strapi-php (the CMS Sitlab uses) | 1337 |
| `apps/cms-node` | Strapi on Node, the same version (the reference) | 1338 |
| `apps/cms-camis` | the same model generated by [CAMIS](https://github.com/hynding/camis) into Laravel + Filament, serving Strapi's REST API | 1339 |
| `apps/web` | the PWA (Vite + React + TypeScript, `vite-plugin-pwa`) | 5173 |

Anything that behaves differently between the two CMS apps is a strapi-php bug to fix upstream.

## Layout

```
schema/                  the content model, the one place to edit it (Strapi schema.json format)
  api/<type>/content-types/<type>/schema.json
  components/story/*.json
apps/cms-php/            strapi-php project (create-strapi-app, vanilla template)
apps/cms-node/           Strapi project (npx create-strapi-app@5.56.0, TypeScript)
apps/cms-camis/          CAMIS project imported from apps/cms-php (generated/ is built, not committed)
apps/web/                the PWA
conformance/             HTTP fixtures run against both CMS apps, with a response diff
scripts/sync-schema.mjs  copies schema/ into both apps (and --check, --pull)
scripts/init-env.mjs     creates each CMS app's .env with fresh secrets
```

## Content model

| Type | Holds |
| --- | --- |
| Story | title, logline, synopsis, format, genre, status; its characters, plot lines, scenes and sources |
| Character | name, role, summary, backstory, portrait, traits (component) |
| Character arc | one character's change across one story: start and end state, beats |
| Plot line | A/B/C plot, subplot or running gag, with beats tagged by mood (humor, drama, tension...) |
| Scene | position, location, time of day, summary, screenplay text, storyboard frames |
| Source | researched public material: URL, kind, publisher, license, date accessed, notes |

## Getting started

Needs PHP 8.3 (`pdo_sqlite`, `intl`, `gd`), Composer, and Node 20+.

```sh
npm run setup        # .env files with fresh secrets, composer + npm installs
npm run dev:php      # strapi-php admin at http://localhost:1337/admin
npm run dev:node     # Strapi admin at http://localhost:1338/admin
npm run dev:web      # the PWA at http://localhost:5173
```

Create an admin in each CMS on first visit. The content API is closed by default: for the PWA, create
an API token in each admin (Settings > API Tokens) and put it in `apps/web/.env.local`
(see `apps/web/.env.example`).

Both CMS apps use SQLite (`apps/*/.tmp/data.db`) for now. The deployed app will use MySQL: set
`DATABASE_CLIENT=mysql` and the `DATABASE_*` connection variables; the Node app also needs the
`mysql2` package then.

## The CAMIS backend

`apps/cms-camis` is the content model as a [CAMIS](https://github.com/hynding/camis) project, made
with `camis new apps/cms-camis --from-strapi apps/cms-php --targets filament`. CAMIS generates a
Laravel 12 + Filament app that serves the same Strapi REST API, so the PWA and the conformance suite
run against it unchanged. It needs the camis repository checked out next to this one (its CLI is
not published yet):

```sh
cd apps/cms-camis
camis scaffold filament generated/filament   # the Laravel host app (once)
camis build                                  # generates the overlay into generated/filament
cd generated/filament
cat ../../deployment.env >> .env              # upload type lists, page sizes, sessions (once)
php artisan migrate && php artisan db:seed --class=RolePermissionSeeder
php artisan camis:admin admin@sitlab.local   # an admin who may sign in at /admin (optional:
                                             # the conformance runner registers one on a fresh database)
cd ../../../.. && npm run dev:camis          # http://localhost:1339/admin
```

`roles.json` gives Strapi's `public` and `authenticated` roles (no grants, so the content API is
closed, as in the other two) and a `super-admin` role, the one that signs in to the admin. Admins
are their own accounts, as in Strapi: they never appear in `/api/users`. CAMIS serves Strapi's admin
API for them (`/admin/login`, `/admin/api-tokens`, …), so the conformance runner signs in to it like
the other two apps. For the PWA, create a full-access API token in the admin
(Settings > API Tokens, `/admin/settings/api-tokens`).

**Upgrading an app scaffolded before separate admin accounts** (camis before hynding/camis#53):
`camis build` (it replaces `config/auth.php`), add `->authGuard('admin')` after `->login()` in
`generated/filament/app/Providers/Filament/AdminPanelProvider.php`, `php artisan migrate`, run
`php artisan camis:admin <email>` again for each admin, then delete their old rows from `users`,
where the API still lists them. `php artisan strapi:import-admins --database=../../../cms-php/.tmp/data.db`
brings cms-php's admin accounts over instead, with their passwords.

`deployment.env` is cms-php's `config/plugins.php`, `config/api.php` and `config/middlewares.php` as Laravel settings: the
upload allow and deny lists (an SVG is refused, as in strapi-php), the REST page sizes and the
refresh-token sessions. CORS follows Strapi's defaults (any origin, with credentials, which the PWA
needs); set `CAMIS_CORS_ORIGIN` to a comma-separated list to narrow it.

`camis.json` is imported from `apps/cms-php`, so it follows `schema/` only when re-imported: after a
model or config change, run `camis new` again into a scratch directory and copy its `camis.json`
and `roles.json` here, write `deployment.env` with
`camis import strapi apps/cms-php --out /tmp/ir.json --env-out apps/cms-camis/deployment.env`, then
`camis build`.

Checked end to end on 2026-11-14 (hynding/camis#66): all fixtures pass on strapi-php and CAMIS, and
an export from cms-php imported with `php artisan strapi:import` answers the content API the same,
timestamps to the millisecond. What still differs from strapi-php:

- After `POST /api/auth/logout`, CAMIS refuses that session's access token at once; strapi-php honours
  it until it expires (the PWA drops it on logout either way).
- `GET /api/i18n/locales` is a 404, as no sitlab type is localized; strapi-php lists `en`.
- With Draft & Publish off, `publishedAt` repeats `createdAt`; strapi-php stores its own, a
  millisecond or two apart.
- An app built before camis#66 keeps second-precision timestamp columns on MySQL/Postgres until they
  are rebuilt (`php artisan migrate:fresh` plus an import, or recreate the tables).

## Changing the content model

1. Edit `schema/` (or edit in one app's Content-Type Builder, then `node scripts/sync-schema.mjs --pull php`
   or `--pull node`).
2. `npm run schema:sync` copies it into both apps and adds a default router, controller and service
   for any new type. Custom code in either app is never overwritten.
3. `npm run schema:check` fails if the apps and `schema/` disagree.

## Conformance

With both CMS apps running:

```sh
npm run conformance                    # every fixture, both backends
node conformance/run.mjs --only php    # one backend
node conformance/run.mjs validation    # fixtures whose name contains "validation"
node conformance/run.mjs --only php,camis   # strapi-php and CAMIS
```

The runner signs in to each admin (registering `admin@sitlab.local` on a fresh database; override
with `CONFORMANCE_ADMIN_EMAIL` / `CONFORMANCE_ADMIN_PASSWORD`), creates a temporary API token, runs
`conformance/fixtures/*.json`, and deletes the token. Each step is checked against its `expect`, and
the backends' responses are diffed against the reference (Strapi on Node when it runs, otherwise the
first one listed) with ids and timestamps masked. A backend can take a token instead of signing in
(`CMS_PHP_TOKEN`, `CMS_NODE_TOKEN`, `CMS_CAMIS_TOKEN`).

### Known differences

- **Plugins enabled by default**: `hynding/strapi-php` is one package, so the PHP app also has GraphQL
  (`/graphql`), documentation and sentry, which a vanilla Node app does not.

## Versions

Both CMS apps track Strapi **5.56.0**, the version strapi-php mirrors. Each app's `package.json`
pins every `@strapi/*` package to 5.56.0 with `overrides`: without them npm resolves some internal
`@strapi/*` dependencies to a newer release, which in the Node app made a 403 come back as a 500.

strapi-php is not on Packagist yet, so `apps/cms-php/composer.json` pulls `hynding/strapi-php` from
GitHub (`dev-main as 5.56.0-beta.1`). Once it is tagged and published, switch to `"^5.56"` and drop
the `repositories` entry.
